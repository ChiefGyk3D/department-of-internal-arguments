Installer: ownership requires the state file (issue #40, unit 2 of 4 for #31). A behavior change, with the lead block and the adopt step (#42) still to come.

- A file is overwritten, updated or removed only when the state store holds a digest that matches its bytes. The marker stays in the file for people and for `--list-managed`, but it is no longer the authority: a clone, synced dotfiles or a forged marker plus matching hash is `unverified` and left alone (`unverified (refused; --adopt records it, --force-edited replaces it)`, exit 1, byte-identical afterwards). A recorded file whose bytes changed is `edited`; putting the recorded bytes back makes it owned again.
- Limit, stated plainly: ownership is the installer's own state record, not the marker, and a marker hash is not a signature. Anyone who can write the state file as you or as root, roll it back, or control `HOME` or `DOIA_STATE_DIR` can still make a forged file read as installed (the threat model in `scripts/state.py` names this).
- `--force-edited` now also replaces `unverified` files and records the new digest. A file with no marker is never touched. Release 0.2.0 files with a known body are accepted as before and recorded after replacement.
- A destination whose bytes equal exactly what this release would write is recorded on `--apply` (checked against the sources, not the marker) and not rewritten. Entries for files that no longer exist are pruned on the next `--apply`.
- Two-phase write under the lock: `--apply` saves the new digest as pending before it writes, writes through the existing atomic helper, and promotes a digest only for a path whose write returned (`settle`), even when a later write failed. A crash between the phases leaves new files `unverified` and already owned ones accepted under both digests; a re-run converges. A second installer is refused while the lock is held.
- Fail closed: a state file that is unreadable, invalid, tampered, from another target or layout, locked, owned by someone else or in a forbidden place refuses every write run, `--force-edited` included. A dry run and `--list-managed` never create the state directory; `--list-managed` still works read-only, reports `unverified` and prints a `state:` line.
- State location: the exclusion now applies to the install roots (the directories the installer writes into), not to the layout's nominal target. `scripts/state.py` gains an optional `roots=` list on `load`, `load_or_empty`, `lock_held` and `Store`; the single-target form is unchanged (project layout). With `--layout user` and `--adapter codex` on your home directory the default `~/.local/state` is accepted; a state directory inside `~/.claude`, `~/.codex` or `~/.agents`, or an ancestor of one, is refused, an explicit `DOIA_STATE_DIR` included.
- The guard table in `tests/test_state.py` goes from 97 to 105 rows (the `inside target` row now names the single-target branch, and seven rows cover the install roots); `EXPECTED_ROWS` is 105.
- Tests: `tests/test_install_state.py` (the forged-marker reproduction from #31, missing, corrupt and tampered state through the CLI, edit and restore, edit then forge the marker hash, crash between phases in a real process, lock contention, pruning, symlinks, planted files, state from another target, location rules for both layouts); the other installer test files run against a private `DOIA_STATE_DIR` (`tests/state_fixture.py`) and their "older release" fixtures record the digest the way an install would.
- Upgrading: files installed before this release have no record. Files equal to the current release are recorded on the first `--update --apply`; older ones show as `unverified` until `--update --force-edited --apply` (or the adopt step, #42). See `docs/install.md`.

Installer: lead block ownership through the state file (issue #41, unit 3 of 4 for #31).

- The `--lead FILE` block is owned only when the installer's state file agrees: an entry of kind `lead`, keyed by the instruction file's relative path, holding the sha256 of the block body (LF endings, so a CRLF conversion does not change it). A block whose begin line hashes its own body but has no entry, for example in a CLAUDE.md the installer never wrote, is `unverified`: `--update` refuses it, the file stays byte-identical, and `--update --force-edited` replaces the block only. A block that differs from its entry is `edited` and is refused the same way.
- A re-run whose block equals this release's block changes nothing in the file and needs no `--update`; the entry is recorded on `--apply` (a dry run records nothing). Updating or forcing a block records the new digest through the same two-phase write as the role files; entries for instruction files that no longer exist are pruned.
- `--list-managed --lead FILE` gains the status `unverified` (a consistent block with no entry, or no usable state file); exit 3 like every status but `current`.
- Unchanged: the text around the block is never touched; a hand-edited block, a malformed marker, a symlink, a non-UTF-8 file and a file over 1 MiB behave as before. The state location and trust rules are unchanged. An entry of another kind at the same path is not a lead record (and a lead record does not vouch for a role file); `--lead` naming a role file's path is refused.
- Limits: `--adopt` (record an existing block without replacing it) is not part of this change (#42); until then `--update --force-edited` is the way to bring a block with no entry under management. A block equal to this release's text is recorded without being rewritten, as for role files: the content is checked against this checkout, which proves the text and not who placed it.
- Tests: `tests/test_lead.py` gains `LeadOwnership` (forged block refused with the file byte-identical, listing, force, recorded update, swapped block, rerun and CRLF, two layouts, text around the block, kinds, pending-only entry, pruning, unusable state). `scripts/mutation_check.py` (issue #43, unit 1 of #25): a helper that proves a test bites without touching the reviewer's checkout.

- `python3 scripts/mutation_check.py --repo PATH --head SHA --revert SHA_OR_PATCH --test "CMD" [--scratch DIR]` clones the head with `git clone --local --no-hardlinks` into a new 0700 directory (default under `~/.local/share/doia-mutation/`, never `/tmp`), runs the test at head (must pass), reverts the named commit's non-test hunks or a given patch (must fail), restores with `git checkout --force --detach` and `git clean`, runs the test again (must pass), and checks `git status --porcelain` and `git diff SHA` are empty after the restore and after the last run. One JSON object on stdout; exit 0 `bites`, 2 `vacuous`, 3 `inconclusive` (anything not clearly a bite, including usage errors). The copy is deleted on `bites` and kept on any other result (`--keep` forces it).
- The source repository's status, content of dirty files, HEAD, refs, stash, config and index are hashed before and after (`source_repo_unchanged`); a change makes the verdict `inconclusive`.
- The head is treated as untrusted: no shell, argument lists only, a sanitized environment (no inherited secrets; caches and `HOME` inside the disposable directory), no user or system git configuration, hooks, fsmonitor and the source's filter drivers switched off, a timeout and an output cap on every subprocess with a process-group kill, symlinked, absolute, `..` and `.git` revert paths refused, and a scratch directory that equals, contains or lies inside the repository refused. Best-effort network removal for the test commands through `unshare --net` (`network_isolation` in the JSON).
- Not a sandbox, and the docstring says so: a test is arbitrary code running as the invoking user and can write to the source repository by absolute path (detected and reported, not prevented); without `unshare` there is no network isolation; a process that leaves its process group escapes the timeout kill.
- Round 2 (adversarial review): the test and every git step of the tool run in a user + network + PID namespace (`unshare --kill-child`), so nothing the test started outlives a run; where the host refuses it the JSON says `process_isolation: none` and the claim is renamed `source_unchanged_at_check` (the source is hashed after the run and again after `--settle` seconds). After the test has run the tool reads no git metadata the test could write: each step uses a new random 0700 bare repository in a private directory (own config and index, objects from a private copy made before the test ran, an empty HOME and XDG_CONFIG_HOME, no inherited GIT_* variable, `core.attributesFile`, `core.excludesFile`, hooks, fsmonitor, pager, ssh, askpass, credential and external-diff overrides, `protocol.allow=never`). SIGINT, SIGTERM and SIGHUP kill the whole run and exit 3; `-h` and usage errors exit 3; `--clean-old DAYS` (default 7) prunes this tool's old kept copies; `--isolation auto|net|none`. The docstring states what `bites` does not prove and what the isolation does not cover (files, unix sockets, identity, secrets): run untrusted heads as a throwaway user, container or VM.
- Round 3 (Codex cyber-tier pass and automated review): a `bites` verdict now needs both the network and the PID namespace; a degraded run is `inconclusive` unless `--allow-degraded-isolation` is given (then the JSON says `isolation_degraded: true` and exit 0 is the weaker contract). The private trusted repository is hidden from the test by a bind mount in the test's mount namespace (mount source made in the private root and mounted through `/proc/self/fd`; every capability set dropped and read back as zero; shim failures exit 126, never a red code; the hiding is re-checked before every run) and, hidden or not, guarded by a digest of every entry (links and special files refused, never opened) so damage makes the run inconclusive and cannot forge a bite. `--clean-old` deletes only directories carrying an authenticated marker (regular file, owner, mode 0600, random per-installation token and the directory name), through a pinned directory descriptor, bottom-up, every removal relative to its own parent's descriptor, refusing mount points and swapped candidates. Dirty or untracked source files of any size are hashed whole under `--max-source-bytes`. `--red-exit` takes 1 to 125 only and a signal death is `crashed`, never red (the test runs under a tiny PID 1 that reports 128+N). Free space (2.5 times the estimate plus a margin) and `--max-copy-bytes` are checked before any copy and a failed copy is cleaned up. The patch file is read through one descriptor, at most 1 MiB. `--private-parent`, `--hide-private`, `--max-source-bytes`, `--max-copy-bytes`, `--allow-degraded-isolation`; the tests honor `DOIA_MC_TEST_DIR`. New: `tests/test_mutation_check_round3.py`.
- Round 4 (CI and automated review): the before/after check of the source repository now also hashes everything inside its git directories (hooks, reflogs, refs, object files, packs; the common directory of a linked worktree too) under `--max-source-bytes`, so a write there makes the run `inconclusive`. Removing the disposable directories now also works when a test took the permissions off a subdirectory (a `TypeError` used to leave the private directory behind). Owner-only modes are named (`stat.S_IRWXU`) and the post-test git environment is built by `post_test_env`. New: `tests/test_mutation_check_round4.py`.
- `tests/test_mutation_check.py`, `tests/test_mutation_check_confinement.py`, `tests/test_mutation_check_trusted.py`: verdicts, exit codes and each confinement promise, each with a case that proves the guard bites.

Round 2 of the review of the benchmark corpus (issue #47):

- Matching is a deterministic maximum bipartite assignment (augmenting paths, canonical report order), so the score no longer depends on the order of the report when evidence patterns overlap (the rubric text said it did not; the greedy version did).
- The evidence match is stated as a keyword heuristic that cannot detect gaming, and is tightened: patterns carry word boundaries, at least two distinct patterns must hit (`evidence_min` lowers it per finding), and on a diff task the evidence must contain a verbatim code line from the head checkout (`quotes`, verified by `--check`). A test builds a report from the label alone and asserts it scores zero recall on every diff task.
- `diff_sha256` no longer depends on the user's git configuration: every output-changing diff option is pinned on the command line and in `-c`, global and system configuration are not read, and `GIT_*` variables of the caller are dropped. The existing digests are unchanged. A mismatch message names both causes (rewritten history, or a different git version or configuration).

Installer state store, unit 1 of 4 for #31 (issue #39). Library and tests only: nothing in `scripts/install.py` calls it yet (wiring is #40).

- `scripts/state.py`: a trusted per-user record of which installed files this installer owns, kept outside every install root and this repository (`$DOIA_STATE_DIR`, else `${XDG_STATE_HOME:-~/.local/state}/department-of-internal-arguments/`; one `0600` JSON file per target and layout in a `0700` directory). Entries are a relative path plus a body digest (no device or inode, no keyed MAC). `load` returns the entries, `None` for a missing file, or raises `StateError` for anything else. The parser is strict: duplicate keys, NaN, depth over 4, unknown keys, more than 4096 entries, non-normalized paths, any Unicode C* character, line or paragraph separator in a path, two entries that collide after NFC and case folding, digests that are not 64 lowercase hex, absent, null or mistyped fields, size over 1 MiB. A target path must be valid UTF-8 (`save` and `load` both refuse otherwise, so `save` never writes a file `load` cannot read). `save` and `Store` write atomically (temporary `0600` file, `O_EXCL`, fsync, rename, fsync of the directory) under a non-blocking `flock` (`another install is running`), refuse to replace a state file that does not read cleanly, and report a directory fsync failure after the rename as a `StateError` that says the state may already have been replaced.
- Location trust: the base directory (the parent of the state directory) is resolved once with `realpath`, so a symlinked `~/.local`, a `/home` link or a macOS `/var` link works; below the resolved base every step is `O_NOFOLLOW` and no link is followed. The base must be owned by the user or root and not group or world writable unless sticky; the state directory must be owned by the user and not group or world writable. An empty or `/` HOME is refused unless `DOIA_STATE_DIR` or `XDG_STATE_HOME` is set. Errors show only the last two path components. A state directory inside the target or this repository is refused.
- Two-phase update: `with_pending(entries, pending, new=...)` records the digests a run is about to write; a new path is added with `pending_sha256` and no `body_sha256`. `settle(entries, written)` takes the set of paths actually written: written paths get their pending digest, unwritten paths keep the old digest, an unwritten new path is removed, every pending field is cleared, and an unknown path in `written` is an error. A new path is never owned until `settle` promotes it because phase 2 reported that exact path: `accepts(entry, digest)` and `verdict()` return False and `unverified` for an entry with no `body_sha256`, whatever the digest (a digest proves equal content, not who wrote the file, and anyone who controls the target can create the planned bytes). A crashed install therefore leaves its new paths unverified and recovery is the explicit adopt step (#42). For a path that already has a body digest, the pending digest next to it stays acceptable (the file was already ours and the pending bytes are the installer's own next release content). `accepts` and `verdict` are total: only plain dict entries and plain str digests are considered, anything else is False or `unverified`; the mutators raise `StateError` on hostile arguments (NUL or non-text targets, subclasses of str, dict, list or set, wrong containers) and never a raw `TypeError`, `ValueError` or `AttributeError`.
- Typed errors and robustness: no raw `OSError` escapes (reads, the lock, every step of a write, a full disk, an unwritable directory); `StateLocked` ("another install is running") and `StateCorrupt` (the file is not trustworthy) are subclasses of `StateError` so a dry run or listing can tell them apart while a write run refuses either. A killed run's orphaned `.<stem>.<hex>.tmp` files are reaped under the lock (exact name pattern, regular files owned by the user, older than 5 seconds, nothing followed). A closed `Store` refuses `load` and `save` instead of resolving against the current directory. The state directory may not be, be inside, or contain the target or this repository.
- Helpers for the installer (#40): `body_sha256(bytes)`, `state_path(target, layout)`, `lock_held(target, layout)` (read-only probe, creates nothing), `load_or_empty`, `with_entry` and `without_entry` (copy and validate), and `verdict(entries, rel, digest)` which returns `owned` or `unverified` and cannot raise on a missing state file, entry or digest. Hand-off notes are in the module docstring, including that a `--layout user` target equal to the home directory cannot use the default location under it.
- Validation never runs foreign code: every field value, dict key, list member and container is checked with an exact `type(x) is ...` test before any comparison, membership, regex or hashing (a `kind` whose `__eq__` raises used to escape `check_entries` as a `RuntimeError`), and `body_sha256` turns a released, non-contiguous or non-bytes buffer into a `StateError`. `tests/test_state.py` runs hostile objects (raising `__eq__`, `__hash__`, `__len__`, `__iter__`, `__getitem__`, `__bool__`, `__str__`, `__repr__`, hash-colliding keys) through every public function.
- Nothing foreign is ever converted or run: error text renders only an exact `str` (or `int`) and shows `?` for any other object, so `str()`, `repr()` and `format()` are never called on untrusted input (a `__str__` that raised `SystemExit` or `KeyboardInterrupt` used to escape from `state_key`, `without_entry`, `settle` and `with_pending`); targets must be an exact `str`, `PurePosixPath` or `PosixPath` (a foreign `__fspath__`, a `Path` subclass or a `str` subclass is a `StateError`); `body_sha256` is stricter than before and now rejects `bytes` and `bytearray` subclasses (exact `bytes`, `bytearray` and `memoryview` only). Tests lock the exact-type helper against `isinstance` (subclasses, a spoofed `__class__`, `bool` for `int`).
- The never-leaks promise is stated for the exact list of functions that take caller data; `parse`, `check_location` and `serialize` are now the internal `_parse_strict`, `_check_location` and `_serialize` (nothing outside `state.py` and its tests used them) and take trusted arguments. `_oserr` shows only the class name for a `strerror` that is not an exact `str`.
- The guard table has 97 rows and the test asserts that exact number, so it cannot shrink unnoticed.
- Provenance, stated in the module docstring: `owned` means the content matches a digest the installer recorded, not that the installer wrote those bytes; for an already-owned path the pending digest means owned for the pending content (the same content the installer would write, so no new authority to overwrite). A caller that needs stronger provenance must not rely on this store alone.
- Tests: a stand-in installer (phase 1, real atomic writes through the installer's write helper, `written` recorded only after each successful write, phase 2) proves that only paths really written become owned, including the case where an attacker pre-placed the planned bytes and the write fails; the kill tests assert that the new state is not visible after a kill before the rename and is visible after the directory fsync.
- The lock file gets the state file's discipline (regular, owned by the user, a single link, mode `0600`), checked before any fix; an existing lock file that fails is `StateCorrupt` and is not repaired, a freshly created one is set to `0600`. Platform limits are in the docstring: flock on network filesystems, the sweep's lstat-then-unlink window and shared-lock starvation by a same-user process (all out of scope).
