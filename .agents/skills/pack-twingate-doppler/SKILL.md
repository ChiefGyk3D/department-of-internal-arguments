# Pack: Twingate and Doppler

Status: written 2026-10-30 (issue #83, under #78) from the maintainer's measured lessons and vendor documentation, never from model memory. The pack benchmark of #73 is pending, so treat this as a checklist. Every claim is VERIFIED (a vendor page read on the date shown, or a run the notes record) or INFERRED (reason given).

## Limits

1. **The secret value is never read, printed, logged or passed to an agent.** Work with names only: the secret's name, its project and config, the variable it maps to. The tool supplies the value at run time (`doppler run -- <command>`, a CI fetch step, a headless client reading a key file); the value never enters a prompt, a brief, a report, a commit, a log or a command line. Never run a command whose job is to print a value to look at it. (Source: maintainer notes, 2026-09 and 2026-10; Doppler documents `--plain` as a way to write a value to a file or process, https://docs.doppler.com/docs/secrets, fetched 2026-10-30, VERIFIED.)
2. **Name-only checks exist; use them.** The Doppler API lists secret names without values (`/v3/configs/config/secrets/names`, https://docs.doppler.com/reference/secrets-names, fetched 2026-10-30, VERIFIED). Prove a secret exists by its name, and that a job received it by the job succeeding, never by echoing it.
3. **Least privilege, and one request for the whole job.** Before asking for any token, scope or consent, write the plan, list every call it needs (including the likely fix if step one fails), look up the exact scope names, and ask once for the union, naming each scope and why. Never offer a broader grant as the fallback; if a scope name is unconfirmed, look it up or ask for a screenshot of the scope list. When the job ends, drop the write scopes yourself or file a card that says they are still open. (Source: maintainer notes, 2026-10-25: a read-only grant was recommended, a delete returned 403 eleven minutes later for a fix that was already foreseeable, and the maintainer had to consent twice.)
4. **New automation gets a new, narrow credential.** A scoped app installation, a rotated token, or an OIDC identity; never a user-scoped personal token that acts as the maintainer with account-wide reach and a long life. (Source: maintainer notes, 2026-10-05, a ruling after a personal token was proposed for CI.)
5. **Never search the secret stores for a credential to reuse.** Do not list or read secret names or values in Doppler (or any store) to find a token that "would work". The host's classifier denied exactly this on 2026-10-25; a credential lookup was allowed only after the maintainer named the access in his own message. Ask for the credential the plan names. (Source: maintainer notes, 2026-10-25.)
6. **Twingate must be on for lab access, and if it is not, tell the maintainer before any workaround.** When the lab or a local service is unreachable, stop that work, report the exact failure and what you did not check, and wait for his decision: troubleshoot or a temporary exception. A temporary exception is explicit, scoped to named tasks, and ends when he says. A hook line saying to route elsewhere is not his approval. (Source: maintainer notes, 2026-10-22, 2026-10-25 and 2026-10-29: briefs said the server was unreachable with no test and no message, and work was routed around it before he was told.)
7. **Restart the client first.** A Twingate client that shows `online` with valid authentication while every path times out was fixed by restarting the client service, after several turns of route and port probing. Offer the restart in the first or second turn with the full command; the maintainer runs `sudo` in his own terminal. Diagnose deeper only if it does not fix it. (Source: maintainer notes, 2026-10-30, observed.) After a fresh boot the usual cause is a Twingate sign-in that only he can complete (maintainer notes, 2026-10-29).

## Twingate

- **Zero trust by default.** A user reaches a Resource only through a Group that holds it and only after the Resource's security policy is met. Twingate denies traffic by default. (Source: https://www.twingate.com/docs/resources and /groups, fetched 2026-10-30, VERIFIED.)
- **Service accounts are for machines.** A Service holds Resources, and security policies do not apply to it: any valid Service Key opens everything assigned to it. A Service Key is shown once at creation, expires after 365 days by default (set at creation, unlimited is allowed), must be revoked before it can be deleted, and cannot be reactivated. Use a unique Service Key per system (each is rate-limited separately). (Source: https://www.twingate.com/docs/services, fetched 2026-10-30, VERIFIED.) The plan needed for service accounts is not stated on that page; a pricing page read on 2026-10-22 said a plan above the entry tier, and one reviewer account showed no service-accounts page, so check the actual plan before designing (INFERRED, maintainer notes).
- **Headless clients take a key file, not a typed secret.** Linux: `twingate setup --headless <key file>`. In Docker, the key is mounted as a file and the container needs `/dev/net/tun` and the `NET_ADMIN` capability; engines that cannot add capabilities (AWS Fargate) are unsupported. In Kubernetes keep the key in a Secret, not the manifest. (Source: https://www.twingate.com/docs/linux-headless, fetched 2026-10-30, VERIFIED.)
- **Connectors need outbound only, never inbound.** Open nothing inbound on the Connector host; the documented outbound set is TCP 443, TCP 30000-31000 and UDP, and a restrictive egress rule that omits UDP broke connectivity in the maintainer's build. (Source: https://www.twingate.com/docs/connector-best-practices, fetched 2026-10-30, VERIFIED; maintainer notes, 2026-10-10.)
- **Connectors: two per network, a unique pair of tokens each.** Reusing a token pair fails the second Connector. Updates are about monthly; update one Connector at a time, keep the same tokens, and expect the Controller to reject a Connector below its minimum version. (Source: https://www.twingate.com/docs/connector-best-practices and /upgrading-connectors, fetched 2026-10-30, VERIFIED; the maintainer updates Connector containers manually.)
- **A piped installer left Connectors dead; the vendor's own Terraform pattern worked.** Write the Connector config file with mode 0600, install from the package repo with the signing-key fingerprint pinned, enable the service, and count success only when it is active. The pipe as the cause is INFERRED. The repo signing key has an expiry date; calendar it. (Source: maintainer notes, 2026-10-10.)
- **API tokens come in three levels:** Read only, Read & Write, and Read, Write & Provision (the last mints Connector tokens and Service Keys). Grant the lowest level and use the allowed-ranges setting (up to 10 CIDR or IP entries). Default limits: 60 reads and 20 writes per minute, then HTTP 429. (Source: https://www.twingate.com/docs/api-overview, fetched 2026-10-30, VERIFIED.)

## Doppler

- **Runtime: a service token is read-only and reaches a single config.** It can carry write access or an expiry (an ephemeral token deletes itself), is shown once at creation, and can be revoked at once. Never use a CLI or personal token in a live environment, because it carries the creator's write access. A revoked token still lets the CLI read the last fetched secrets from its encrypted fallback file. (Source: https://docs.doppler.com/docs/service-tokens, updated 2025-05-29, fetched 2026-10-30, VERIFIED.) Keep token values out of shell history and out of any command line you share.
- **Service accounts replace user tokens for machines.** A new service account can do nothing until given a workplace role and project access (one environment is enough). Tokens can be rolled; a new one is shown once. Service accounts need the Team or Enterprise plan. (Source: https://docs.doppler.com/docs/service-accounts, updated 2026-03-23, fetched 2026-10-30, VERIFIED.) The maintainer's pattern: one service account per repository, Viewer on one shared CI config only (2026-09-21).
- **CI uses OIDC identities, not long-lived tokens.** An identity lets a service account authenticate with the CI provider's OIDC token; the identity ID is configuration, not a secret, and the resulting API token is short-lived. Plan: Team or Enterprise. Audience and subject claims are required; avoid wildcards, and list the exact refs. In GitHub the workflow needs `id-token: write`. (Source: https://docs.doppler.com/docs/service-account-identities, updated 2026-04-20, and /github-oidc-examples, fetched 2026-10-30, VERIFIED.) Measured lessons:
  - A repository created from mid-2026 uses a longer immutable subject form; an identity that lists only the plain form failed with a claim-mismatch error. Doppler has no identity update call, so new identities were created with all subject forms and the old ones deleted (2026-10-04).
  - A pull-request event carries a different subject (`...:pull_request`) that the identities exclude by design, so jobs triggered by a pull request cannot fetch secrets; do not widen the subject to fix it. (Maintainer notes, 2026-10-05.)
  - The fetch action masks what it fetches in CI logs; the CLI path does not mask automatically, so mask values yourself. (Vendor page above, VERIFIED.)
- **Visibility:** Unmasked, Masked, or Restricted. A Restricted value cannot be viewed in the dashboard after saving and is returned only to non-user tokens, but anyone who can create a service token can still read it through the CLI or API. (Source: https://docs.doppler.com/docs/secret-visibility, fetched 2026-10-30, VERIFIED.)
- **Activity log:** every change, including rotations, is logged in the activity log, and a config log can be rolled back. (Source: https://docs.doppler.com/docs/workplace-logs and /secrets, fetched 2026-10-30, VERIFIED.)

## Rotation: what it breaks

- **Rotation breaks anything that cached the old value.** Doppler's two-secret strategy keeps an active and an inactive instance, switching halfway through each interval, so a consumer has time to restart. Set the rotation interval to the longest restart cycle of any consumer, plus a buffer. If you change the rotated system by hand, Doppler pauses rotation. Rotation needs Team or Enterprise. (Source: https://docs.doppler.com/docs/secrets-rotation, updated 2025-10-22, fetched 2026-10-30, VERIFIED.)
- **A rotated secret exposes name and value pieces.** One vendor's rotated token produced a pair of secrets named with `_NAME` and `_VALUE` suffixes; point the consumer at the value reference. The managing key was a user token; an account-owned token in that field was rejected as an invalid format (token kind as cause INFERRED; a user token worked). (Source: maintainer notes, 2026-10-25, observed.)
- **Provision the new credential before you revoke the old.** Deleting a CI secret never revoked the provider's token; revocation happens at the provider. A freshly minted replacement leaves nothing to rotate, only the superseded token to revoke. (Source: maintainer notes, 2026-09-21.)
- **Calendar every expiry.** Doppler has no reminder feature; a service token, a cloud API token (90 days), a Twingate API key and the Connector repo signing key each expire. File an issue with the date when the token is created. (Source: maintainer notes, 2026-09-21 and 2026-10-10.)
- **Leak response:** revoke at the provider first, then replace in Doppler, then check the activity log and consumers. Build secret-shaped test fixtures at run time: the scanner reads every branch, so one literal reds every pull request. (Source: maintainer notes, 2026-10.)

## Where secrets leak

- **A .env file in a parent directory.** A runner found a parent checkout's `.env` with a secret-manager token and posted 20 duplicates to a live channel. Tests stub the loader and clear the environment; `env -i` alone does not protect. (Source: maintainer notes, 2026-09-03.)

## How to verify (commands)

- **No value leaked:** the report, brief and logs hold secret names only; search them for token prefixes and long random strings and show no hit.
- **Names, not values:** the existence check reads the secret-names endpoint or a job result; no command in the transcript prints a value.
- **Scope plan:** the access request lists every call and scope up front, and the session returns to read-only afterwards.
- **OIDC:** a CI log shows the OIDC login mode and no stored static token for that job; the identity lists exact refs, not wildcards.
- **Twingate:** `twingate status` and a path test show the failure before any workaround; the maintainer was told that turn.
- **Rotation:** list each consumer's restart cadence next to the rotation interval; the interval is not shorter than the slowest.
- **Privacy:** no tenant name, host, address, project or token name, or identity ID in the report; run the placeholder sweep.
